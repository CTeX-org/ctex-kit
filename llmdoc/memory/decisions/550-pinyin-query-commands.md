# 决策：#550 拼音查询命令的接口与实现形状

## 背景

Issue #550（2020 年的 wishlist）希望把「查拼音」从「排注音」里拆出来，提供四个命令：返回拼音、首字母、声母、韵母，并能选择声调形式。

真实动机在评论里：用 `glossaries` 加 `bib2gls` 做中文索引时，CLDR 默认把中英文混排（「汉字」和「happy」都进 H 组），想按拼音首字母把中文条目分开，就得手工给每个索引项加前缀。issue 里有 stone-zeng 五年前给的原型。

调研结论发在 [issue 评论](https://github.com/CTeX-org/ctex-kit/issues/550#issuecomment-5203109297)，其中的数据是下面几个决策的依据：

- 44360 个单音字的首字母**全部**能归入 `a`–`z`，零例外（缺的 `i`／`u`／`v` 正是拼音里不作首字母的三个）；
- 原型的声母／韵母正则要求必须匹配到声母，对 6268 个字（14.1%）返回空——它们以 `y`、`w` 或元音开头；
- 5965 个多音字里 3869 个（64.9%）的读音跨不同首字母组。

## 决策

九项，逐条与用户确认。

| # | 决策 | 结论 |
|---|---|---|
| 1 | 实现范围 | 四个命令都做 |
| 2 | `y`／`w` 切分 | 双模式，`scheme=literal`／`official` |
| 3 | 默认 `scheme` | `literal` |
| 4 | 多音字 | 默认取首选读音，星号形式取全部 |
| 5 | 声调形式 | `tone=mark`（默认）／`number`／`none`／`v` |
| 6 | `number` 下的 `ü` | 写作 `v` |
| 7 | 可展开性 | 预生成数据表，四个命令都可展开 |
| 8 | 载入策略 | 包选项 `query` 按需载入 |
| 9 | 引擎覆盖 | 只支持 XeTeX |

命名：`\xpinyinvalue`、`\xpinyininitial`、`\xpinyinshengmu`、`\xpinyinyunmu`。统一用 `xpinyin` 前缀；声母／韵母用汉语拼音的说法，避开英文 `initial` 的歧义（它既可指首字母也可指声母，原型里正是用 `Abbr` 与 `Inital` 两个词区分的）。

## 理由与代价

### 默认 `literal`（决策 3）

`literal` 把 `y`／`w` 当声母，只做字面切分；`official` 依《汉语拼音方案》把它们视为介音 `i`／`u`／`ü` 的书写形式，声母为空并把韵母还原成音位形式（`wang` → `uang`，`yue` → `üe`）。

选 `literal` 作默认的理由是输出可预测、声母加韵母拼回去等于原拼音，写测试断言时可以直接比对。代价是语言学上不严谨，需要在手册里说明。

`yo` 一类（395 个字）按「`y` 后接其他元音则 `y` 变 `i`」的通则处理成 `io`。这个音节的实际读法有不同意见，本包不对它单独取值，手册里标注为已知争议点。

### 可展开性决定了整个实现形状（决策 7）

索引排序键与 `bib2gls` 字段都要求参数能展开成字面文本。实测：纯查表的命令可以完全展开（`\edef`、`\index`、`\csname` 三种场景都通过）；但去声调要拆开预组合字符，而 expl3 里做这件事的 `\char_to_nfd:N` **无法在可展开上下文里使用**（嵌在 `\edef` 里报 100 个错）。

因此改为在生成数据库时预先算好「字母加声调数字」形式（`zhong1`、`nv3`），运行时只做取值与字符串处理。四种输出都由它派生。

代价是多一份 1.07 MB 的数据表，这直接引出决策 8。

### `query` 按需载入（决策 8）

实测当前载入主数据库耗时约 0.33 秒、占用 100 万 string characters（上限 540 万）。查询表与主表同量级，而只用注音功能的用户不需要它。因此查询表单独成文件，用包选项按需载入，主表逐字节未变。

未加 `query` 而调用查询命令时明确报错，而不是让命令展开成空——后者会让排序键静默变成空串，出错的地方离原因很远。

### `number` 下的 `ü` 写作 `v`（决策 6）

依据是包内既有约定：`\pinyin` 的输入形式就是 `v`（手册例子 `\pinyin{nv3hai2zi}`、`\pinyin{lv2zi}`），内部由 `\@@_replace_v:n` 把 `v` 映射成 `ü`。于是 `number` 形式输出 `nv3` 可以直接馈回 `\pinyin`。

若写成 `nu3`，馈回 `\pinyin` 会得到「努」的读音 `nǔ` 而不是「女」的 `nǚ`，属于不可逆且错得隐蔽。

### 只支持 XeTeX（决策 9）

查询命令要取汉字码位。实测 pdfTeX 加 CJKutf8 路线上：直接用反引号取码位完全失效（输出为空）；改用包内既有的 `\@@_to_unicode:n` 会输出乱码并报 10 个错，因为它依赖 `\CJK@plane`，需要字符级钩子提供的上下文。

要支持 pdfTeX 得另外设计一套取码位路径，而本需求指向的 `glossaries`／`bib2gls` 本身面向现代引擎。因此这组命令只在 XeTeX 下提供，加 `query` 选项时若引擎不符则报错。

**表述订正**：初版写成「只支持 Unicode 引擎（XeTeX 与 LuaTeX）」，审查时被证否——xpinyin 的包级门禁是 `\bool_lazy_or:nnF { xetex } { pdftex }`，**LuaTeX 下宏包整体 `\msg_critical` 中止**，根本走不到查询命令。把包级限制与本功能限制混为一谈，还会把 pdfTeX 用户导向一个同样不可行的引擎。引擎判据也相应从「不是 pdfTeX」改为「必须是 XeTeX」：日后若包级门禁放行别的引擎，正向判断不会把它默认当成可用。

## 审查后修正的两处

**`\index` 不展开参数，原先手册给的核心用法不生效。** 这是整个可展开性设计所服务的场景，却在手册里给错了写法：`\index` 先 `\@sanitize` 再把参数原样写进 `.idx`，所以 `\index{\xpinyinvalue{汉}@汉字}` 存进去的是这串命令本身而不是 `han`。端到端跑 makeindex 得到的顺序既不是拼音序也不是码位序。

更糟的是同一场景下报错也不会出现：`\@@_query_missing:n` 是 `protected` 的，命令没被展开就不会触发它，于是未加 `query` 选项的文档零错误编译、静默产出错误索引——正是本决策想避免的失败方式。

修法是手册改为给出 `\edef` + `\expandafter` 的写法（已端到端验证：`.idx` 里是 `han@汉字`，makeindex 排出 an／han／zhong 的顺序），并明确写出「`\index` 不展开参数」这条前提及其对报错时机的影响。

**参数校验缺失。** `` `#1 `` 只接受单个字符记号，所以 `\xpinyinvalue{中国}` 会先漏出 `! Missing \endcsname inserted.`、空参数漏出 `! Improper alphabetic constant.`，都是看不出与本宏包有关的底层错误。已在 `\@@_query_dispatch:nnn` 里加一道 `\tl_count:n {#3} = 1` 的检查（用 `\int_compare:nNnTF` 保持可展开），不满足时报专用错误。

## 第二轮审查后的修正：同一失效方式的第二次发作

第一轮把「`\index` 不展开参数」定为阻塞并写进了手册与本文档，但**新写的配方本身仍然没有端到端验证**，于是同一类问题在同一处又出现两次：

**配方缺 `\makeatletter`。** 配方用 `\@tempa` 作中间变量，而正文里 `@` 的 catcode 是 12，`\edef\@tempa{...}` 定义到的并不是 `\@tempa`，产出的排序键是 `han @汉字`（多一个空格）而不是手册断言的 `han@汉字`。makeindex 按字面比较，这会让它与手写的 `han@汉字` 分成两个条目而不合并。已改用普通名字 `\pyindexkey`，并在手册里说明这个坑。

**「能在缺少选项时立刻发现问题」不成立。** `\@@_query_missing:n` 用的是 `\msg_error:nnn`，它是 `protected` 的：在 `\edef` 里既不报错也不展开，会把自己整条原样留在结果里。于是未加 `query` 选项时文档零错误编译，`.idx` 里写进 `\__xpinyin_query_missing:n {汉}@汉字`——**第一轮认定为阻塞、并写进本文档的那个失效方式依然存在**，只是坏键的内容换了。

已改用 `\msg_expandable_error:nnn`（`zhnumber` 在本仓库已有同样用法）。它在可展开的上下文里也会发出错误且不留残余，实测未加 `query` 时现在报 `Pinyin query table is not loaded`。

**参数校验数错了单位。** `\tl_count:n` 数记号，把 `{中}`、`\hz`（汉字存在宏里）各算一个，检查会放它们过去，随后照旧漏出底层 TeX 错误。改用 `\str_count:n`，它先把参数变成字符串再数。

**测试补了最终产物的判据。** 前一版只断言 `\edef` 的中间结果，两个缺陷都因此溜过。现在固定交给 `\index` 的实际字节，并把两个报错场景各拆一个文件——可展开的报错会中断后续断言，同处一个文件时只有前一个有效。

## 接受的限制

**两处韵母不带声调。** `\@@_replace_v:n` 只在 `l`、`n` 之后把 `v` 当 `ü`，所以以 `v` 开头的片段标不出 `ü`（`\pinyin{v3}` 得到 `ǔ`）。受影响的是 `official` 模式的韵母（可能以 `v` 开头）与 `literal` 下「女」的韵母。与其静默给出错的字形，改为输出无调形式。细节记在 `xpinyin/MAINTAINING.md`。

**两种情况不可展开。** `tone=mark` 要经过 `\@@_pinyin:n`，它把内容排版出来而不是返回字符串；带星号的形式要去重，用到列表变量。手册里明确写出：用于排序键时选 `number`／`none`／`v`，并用不带星号的形式。

**声母永远不带声调。** 它只由辅音组成，标不了调。早期实现把声调一律接在切出来的片段后面，「中」的声母排成了 `zh1`——`\@@_pinyin:n` 找不到可标调的元音就把数字原样输出了。

**`scheme` 的判断必须在「取韵母」这一支内部。** 提到外层时 `\xpinyinvalue` 在 `official` 下会返回 `uang` 而不是 `wáng`；它返回完整读音，与切分方式无关。

**星号形式只在结果是纯文本时去重。** `tone=mark` 的输出含 `protected` 的 `\@@_pinyin:n`，`e` 类展开留不下文本，收不进逗号列表；强行去重会把每项变成空（实测输出 `,,,,`）。首字母不受 `tone` 影响，所以「行」的四个读音能正确合成 `h,x`。

## 未采纳

**在命令参数里给选项。** keyval 解析不可展开，把选项放进参数会让整条链用不到 `\index` 或 `bib2gls` 里去。改为用 `\xpinyinsetup` 设置，与包内其他选项一致，并随 TeX 分组恢复。

**只做首字母。** 调研时曾建议缩小到提问者真正需要的那一块（首字母数据零缺口、实现最简单），声母／韵母另开 issue。用户选择四个命令都做。
