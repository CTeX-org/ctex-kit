# 反思：#1057 xeCJKfntef 命令嵌套时的断行边界

## 任务

Issue #1057（带 documentation 标签）报告 `xeCJKfntef` 的装饰命令嵌套使用时断行异常。报告者给了
4 个案例的 MWE 与截图，并对比了 `lua-ul` 的表现。任务是判断这是缺陷还是既有限制，并给出相应处置。

## 结论

这是 `ulem` 的固有约束，不是回归缺陷。处置方式是补文档加补回归测试，不改实现。

`ulem` 只允许最外层的线型命令启动扫描。内层线型命令走 `\UL@onin` 复用外层已经打开的扫描过程，
正文被整段拆进一个固定宽度的盒子，盒子内部不再留有断点，于是整段无法断行。

实测确认的边界如下：

- 命令按装饰的绘制方式分两类。线型命令借 `ulem` 扫描画连续线条：`\CJKunderline`、
  `\CJKunderdblline`、`\CJKunderwave`、`\CJKsout`、`\CJKxout`、`\CJKunderanyline`。符号型命令
  逐字放置独立符号、不经 `ulem` 扫描：`\CJKunderdot`、`\CJKunderanysymbol`。
- 六个命令单独使用都能正常断行，没有 Overfull。
- 两个线型命令相互嵌套时，内层正文整段进入一个刚性 `\hbox`（实测 107.22pt，内部没有
  discretionary），无法断行，Overfull 276.99pt。嵌套的先后顺序不影响结果。原生 `\uline` 嵌
  `\CJKunderline` 同样如此。
- 符号型命令与任何命令嵌套都能正常断行。唯一的例外是 `\CJKunderanyline` 自嵌套失败，因为它
  本身属于线型。
- 发布版 v3.10.4（系统 TeX Live）与工作树 v3.10.5 行为完全一致，溢出量同为 276.99pt。这一点
  证明它是长期存在的约束，而不是本版本的回归。

## 过程中的问题与修正

### 第一次跑 MWE 加载的是系统 TeX Live 的 v3.10.4，不是工作树的 v3.10.5

我直接写了 MWE 就跑，得到的读数其实来自系统安装的 v3.10.4。是后来 `grep` 日志里的宏包路径才
发现的。修正方法是先 `l3build unpack`，再用 `TEXINPUTS` 指向 `xeCJK/build/unpacked`，并且每一次
运行都核对日志里的 `Package: xeCJKfntef` 行确认版本。

`llmdoc` 已有「从源码树验证时必须核对实际加载文件」这条教训，本次是它的又一个实例。值得记下的是
**它为什么容易反复发生**：不指定 `TEXINPUTS`、或者 `TEXINPUTS` 指向的目录不存在时，`xelatex`
不报错也不警告，而是静默回落到系统安装的同名宏包，编译照样成功、读数照样是一组像样的数字。也就
是说这条失效**没有任何主动信号**，只有主动去核对日志才看得见。凡是靠「出错会提醒我」来兜底的
检查项，在这里都不成立，必须写成每次运行都执行的固定动作。

本次的具体后果不算严重（v3.10.4 与 v3.10.5 在这条路径上行为相同，结论没有被带偏），但这纯属
运气——若两版行为不同，我会得出一个方向完全相反的判断。

### 报告者的 MWE 是复合样例，据它判断不出支持边界

原 MWE 的 4 个案例都混合了多个变量：既换命令、又换嵌套顺序、又换正文长度。我如果只跑这 4 个
案例，能得到的最强结论是「嵌套就是坏的」——而这个结论过宽，照它写文档会把 `\CJKunderdot` 的
嵌套一并说成不能断行，而那是错的，手册里恰好还有一个 `\CJKunderdot` 嵌套的示例。

修正方法是自己做控制实验，分两步：先测「六个命令各自单独使用」建立基准，确认单用全都正常；再
逐一测「各种两两嵌套组合」。这样才得出「线型套线型失败、符号型可以自由嵌套」这条准确边界，也才
知道 `\CJKunderanyline` 自嵌套失败不是新现象，而是它属于线型的必然推论。

一般化的教训是：报告者的样例证明「存在一个坏的输入」，它不能划定支持边界。要写进文档的边界必须
由自己设计的、一次只变一个变量的控制实验得出。这在 documentation 类 issue 上比在缺陷类 issue 上
更要紧——缺陷类只要修好那一个案例就有实际价值，而文档写错边界会长期误导所有读者。

### 「间距正确」与「断行正确」是两个独立命题

`xeCJK.dtx` 的「已知问题和兼容性」一节列了一份「间距行为正确」的命令清单，其中包含嵌套组合。
清单本身没有错，但它没有说自己只管间距，读者很自然会外推成「嵌套在各方面都没问题」。issue 作者
正是这样理解的：他先读到嵌套被列为正常，再看到断行出问题，于是判断这是缺陷。

修法是在那份清单处显式声明「本节只讨论 CJK 间距，不涉及断行」，并交叉引用新增的 §3.6.1；同时在
`\CJKunderdot` 的说明处补一句「嵌套后仍然可以正常断行」，并指向新小节。

教训：**文档里的肯定性清单必须说清它保证的是哪一个维度。** 一句「以下命令行为正确」在读者那里会
被读成「以下命令没有问题」，而这两句话的覆盖面差得很远。凡是列举「什么是好的」的清单，都要写上
它的量纲；相邻维度上如果存在已知限制，就要在同一处交叉引用，不要指望读者自己去找。这类问题不会
被任何测试拦住，它只在读者外推出错时才暴露出来。

### 换一个可观察量，能给原本「无法回归保护」的路径补上测试（本次最有价值的一条）

`llmdoc/reference/build-and-test.md:516` 此前明确记载 `\UL@onin` 路径**没有回归保护**，并给出了
结构性的理由：该路径用 `\setbox\UL@box\hbox{{#1}}` 把内容整体装进盒子，内层收缩量本来就出不来，
所以「收缩量丢失」这个症状在那里不显现。实测也支持这个记载——在该分支重新引入缺陷、乃至整段删掉，
全套测试都保持全绿。那段记载末尾还写着一句「若将来找到可观察量……应当补上用例并更新此处」。

本次要固定的行为是「能否断行」。这个可观察量正好落在这条路径上：正文被装进刚性盒子这件事，对
「收缩量」不可见，对「断点」却是决定性的。同一句 `\setbox\UL@box\hbox{{#1}}`，用一个观察量看不见，
换一个观察量就是最直接的证据。

我另外用计数器插桩确认分派确实不同，避免只凭现象推断机制：线型套线型时 `\UL@onin` 计数为 1，
线型套符号型时计数为 0。也就是说新测试的 TEST 1 确实经过这条路径，TEST 3 确实不经过。

可复用的规则：**「症状不显现」不等于「路径不可测」，应当换一个可观察量再判断。** 说某条路径没法
测时，实际说的是「我当前用的那个观察量在这条路径上恒定」。这是观察量的性质，不是路径的性质。
一条被记为「不可测」的路径，正确的处理是把当初的理由写清楚（本仓库这次做到了，正因如此我才能
接上），并把「换观察量」列为待试项，而不是当成永久结论。判断一个候选观察量是否可用，看它是否
依赖那段代码**改变了什么结构**：这里改变的是「正文被装进刚性盒子」，那么凡是受盒子刚性影响的
量（断点、badness、溢出）都是候选，而受盒子边界屏蔽的量（内部收缩量）都不是。

### 把既有限制固定成断言，需要双向判据

要固定的不是「某处修好了」，而是「某条限制存在」。这种断言容易写成单向的：只写几条会溢出的用例，
基线里出现 Overfull 行就收工。问题是这样无法区分「限制确实只影响线型套线型」与「凡嵌套都溢出」。

新测试因此两个方向都有断言：TEST 1、TEST 2 的基线**含** Overfull 行，作为限制存在的证据；
TEST 3 到 TEST 6 的基线**不含** Overfull 行，因为这些组合确实能断行。有了后一组，前一组才不是
空基线的默认结果，文档里「符号型可以自由嵌套」那句话也才有校验。

并做了变异验证：把 TEST 3 的内层从符号型 `\CJKunderdot` 换成线型 `\CJKunderwave`，基线因为多出
Overfull 行而失败（rc 1）。这证明「不含 Overfull」这一侧确实有判别力，不是碰巧通过。

做法与 `boundary-sbox-global01` 固定 `\global\savebox` 那条上游限制同源：既有限制值得固定，理由是
避免日后有人把它误判为回归；而一旦将来确实绕开了它，该项会失败并提示更新文档。

### 写测试时必须避开另一条已知限制的干扰

`fntef-shrink01` 的注释警告过：调用处用宏承载正文（`\CJKunderline{\BODY}`）会触发另一条既有限制，
即宏体在 `ulem` 扫描期间才展开，收缩量同样出不了外层。我最初的探索 MWE 恰好就是用 `\def\BODY`
写的。

后来用字面正文重新测了一遍，结论不变，两种写法同为 276.99pt。但这次复核是必要的：两条限制在这个
样例上给出**同一个数字**，不复核就分不清我量到的是哪一条，也就无法断言这个数字是嵌套造成的。
新测试因此一律用字面正文，并在文件注释里写明理由。

教训：在一个已经积累了多条既有限制的子系统里写测试，先清点这些限制，确认自己的样例不会同时触发
其中两条。共用观察量的多条限制会给出相同读数，此时读数本身不能说明成因，必须靠构造把它们分开。

## Promotion Candidates

以下四条建议提升到 `lessons-learned.md`：

- **「症状不显现」不等于「路径不可测」，换一个可观察量再判断。** 说某条路径无法回归保护时，实际
  说的是「我当前用的观察量在这条路径上恒定」，那是观察量的性质而非路径的性质。把「不可测」写进
  文档时必须一并写清当初用的是哪个观察量、为什么它在那里恒定，好让后来者能接上；并把「换观察量」
  列为待试项，不要当成永久结论。挑选候选观察量的判据是它是否依赖那段代码改变了的结构。
- **把既有限制固定成断言，需要双向判据。** 只写「触发限制的用例会出现症状」是单向的，无法区分
  限制的作用范围；必须同时写一组「不触发该限制、症状不出现」的对照，并对两侧各做变异验证。否则
  不触发的那一侧是空基线的默认结果，凡是写进文档的适用范围都没有校验。
- **文档里的肯定性清单必须声明它保证的是哪一个维度。** 「以下命令行为正确」会被读成「以下命令
  没有问题」。列举「什么是好的」时要写明量纲，相邻维度上有已知限制就在同一处交叉引用。这类问题
  没有任何测试能拦住，只在读者外推出错时暴露。
- **报告者的复合样例证明「存在一个坏输入」，不能用来划定支持边界。** 要写进文档的边界必须由自己
  设计的、一次只变一个变量的控制实验得出：先测各元素单独使用建立基准，再逐一测组合。这在
  documentation 类 issue 上尤其重要，因为文档写错边界会长期误导所有读者，而不只是漏修一个案例。

以下一条建议追加到既有条目，不新增条目：

- `lessons-learned.md` 的「从源码树验证时必须核对实际加载文件」条目可以补上**这条失效没有任何
  主动信号**这一成因：`TEXINPUTS` 未设或指向的目录不存在时，`xelatex` 不报错、不警告，静默回落到
  系统安装的同名宏包，编译成功、读数是一组像样的数字。因此它不能靠「出错会提醒我」兜底，必须写成
  每次运行都核对日志 `Package:` 行的固定动作。本次是该教训在 #1012、#1026、#1047 之后的又一次
  发作，共同点都是「以为自己在测工作树」。

以下属于本次的具体情况，不必提升：

- 线型与符号型的具体命令分类，以及 107.22pt／276.99pt 这两个数值——它们随正文与 `\hsize` 而变，
  属于本 issue 的记录，已写在 `.lvt` 注释与手册新小节里。
- `\CJKunderanyline` 自嵌套失败，是「它属于线型」的推论，不是独立事实。
- 「先清点子系统已知限制，避免样例同时触发两条」这条与既有的「调用处写字面正文 vs 用宏承载正文
  是两条不同的收缩链路」高度重叠，`fntef-shrink01` 的文件注释已经承担了提醒作用，本次只需在新
  测试里照做。
