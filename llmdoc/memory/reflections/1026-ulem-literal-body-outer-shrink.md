# [Task Reflection]

## Task

Issue #1026：`xeCJK-v3.10.5-rc1` 之后，`\CJKunderline`／`\CJKunderwave`／`\CJKunderanyline*` 等装饰在换行时右边界不对齐。用户以为是 #1012 的周期装饰改动引入，实际不是；引入点在更早的 `494d5a72`（#1002 的一部分）。

修复方式：`xeCJK/xeCJK.dtx` 的 `\UL@on` 与 `\UL@onin` 改为先判断语法，再分别走两条路径——正文是「公式尾＋尾随源码空格」时用 `\@@_boundary_ulem_math_tail_space:n` 重排（保留 #1002 的修复），否则保持 `\xeCJK_ulem_left: #1` 的字面展开。新增 `\@@_boundary_if_ulem_math_reorder:nTF` 判断走哪条路径，原来统一处理两种情况的 `\@@_boundary_ulem_math_body:n` 被这两个函数取代。新增回归 `xeCJK/testfiles/fntef-shrink01.lvt/.tlg`。

## Expected vs Actual

- 预期：既然标签和现象都指向 fntef 装饰，根因应该在 #1012 的周期 leaders 或裁切逻辑里，按接点分工那份决策文档定位即可。
- 实际：`git bisect` 式排查证明 #1012 的四个提交都不是引入点；真正的引入点是更早的 `494d5a72`（#1002 inline-math 系列），把 `\UL@on` 的替换文本从 `\xeCJK_ulem_left: #1 \@@_boundary_math_end:n {#1}`（字面记号）改成了 `\xeCJK_ulem_left: \@@_boundary_ulem_math_body:n {#1}`（宏参数间接展开）。子系统标签和现象所指的位置，可以与真正的引入提交完全无关。
- 预期：把内容装进 `\hbox` 量 badness，或者用 `\vbox` 排段落，就能测出收缩量差异。
- 实际：连续写了三版测试都"通过"，但都是假绿——`\hbox`／`\vbox` 的 glue set 会把内外层收缩一并用掉，两版数字完全相同；第三版用 `\def\BODY` 承载正文，宏体本身就触发既有限制，两版又相同。只有「document 主垂直列表里成段排版 + 调用处字面正文」才能分辨出差异。

## What Went Wrong

1. **第一假设方向错了。** Issue 标题和标签都指向 fntef 装饰，先读了 #1012 的决策文档和周期 leaders 实现，排查了半天才确认这条线索是错的，浪费了定位时间。

2. **测试写错三次，每次都显示通过。**
   - 第一版：把正文装进单个 `\hbox` 量 badness——`\hbox` 内部会把所有可用收缩量统一用掉抹平差异，缺陷版与修复版数字完全相同。
   - 第二版：改用 `\vbox` 排段落——同样量不出，两版都是 18.08pt。
   - 第三版：在 `\TEST` 里用 `\def\BODY` 承载正文——宏体本身就会触发既有限制（见下），两版又相同。
   直到第四版改成「document 主垂直列表里成段排版，且调用处写字面正文」才第一次看到差异。

3. **一开始没有先用重新引入缺陷的方式验证测试会失败。** 前三版测试全部显示通过，如果没有主动怀疑并倒回去验证，很可能把假绿当成"修复已验证"上报。

4. **`\showthe` 在 `\TEST` 里会中断执行。** 排查过程中用 `\showthe` 打印中间宽度，导致 `.tlg` 只记录到第一个 `\TEST` 就停止；目标宽度不可达时 `\hbox to` 还会把整份节点列表倒进 `.tlg` 当基线，非常脆弱，容易把调试残留误固化成基线。

5. **并行跑 `l3build save` 和 `l3build check` 互相清掉了共享的 `build/test` 目录**，出现 `No such file or directory` 的假失败，一度误判为测试脚本本身有问题。

6. **对比实验里又踩了一次"实际加载路径与预期不符"的坑。** `TEXINPUTS` 指向工作树后，仍需要在日志里核对实际加载的是不是工作树版本；有几轮对比误以为在测工作树，实际命中的是系统 TeX Live 的同名文件，得出"两者相同"的错误结论。这与 #1012 反思里记录的教训同源，但这次是在对比实验环节而非验证环节踩的。

## Root Cause

`\UL@on` 的正文原本以字面记号留在替换文本里；#1002 为了处理"公式加尾随源码空格"这一种情况，把正文统一改成了通过宏参数间接展开。ulem 自己扫描正文并按源码空格把它切成固定宽度的装饰片段盒（每个片段一个盒子）；正文一旦经过参数间接展开，西文词右侧由边界恢复链补出的 `\CJKecglue` 就会落在片段盒**内部**，其收缩量被盒子固化，无法参与外层段落的断行决策。这一改动本意只是为了让"公式加尾随源码空格"这一种边界情况能正确重排，却把所有正文都改成了间接展开，波及了不需要重排的普通场景。

节点级证据（`\showbox` 深度）：基线中 `hello` 后的 ecglue 在深度 1（片段之间），是 `\cleaders 5.32997 plus 1.665 minus 1.11`；缺陷版中同一枚 ecglue 落在深度 2（片段盒内部），变成 `\cleaders 1.99997 plus 0.96002`，没有 minus。两者自然宽度完全相同（328.08pt），但深度 1 的可收缩总量从 17.22pt 降到 15.00pt，差 2.22pt，正好等于 2 个西文词 × 每词 1.11pt 的收缩量。原始 MWE 的行右端从基线 681px 冲到 722px。

测试写不出来的根因是三版方案分别选错了"能观察到内外层区分"的载体：单 `\hbox`／`\vbox` 都会把外层收缩一并耗尽，抹掉内外层的区别；宏承载正文则是从另一个通道触发了同一类"收缩量出不了外层"的既有限制，恰好和本次缺陷的症状一致却成因不同，掩盖了两者的差异。

## 已接受的既有限制（重要，不在本次修复范围）

把正文写成宏再传入，例如 `\CJKunderline{\BODY}`，收缩量同样进不了外层。实测**发布版本（系统 TeX Live）同样是 18.08pt**，说明这不是本次回归，而是发布版本本来就有的既有限制。这条限制没有修，测试因此必须在调用处写字面正文，不能用宏承载正文，否则会把这条已知限制误判成本次修复的验证对象。

## Missing Docs or Signals

- `xecjk-architecture.md` 目前只记录了 #1002 的 `math-space`／`math-space-frozen` 区分逻辑，没有说明"ulem 正文必须以字面记号留在替换文本、不能经宏参数间接展开"这条更基础的约束；这条约束比公式候选确认更早生效，属于 ulem 集成层面的通用限制。
- 没有一处文档提醒"用单个 `\hbox`／`\vbox` 测收缩量会被 glue set 抹平内外层差异"；这是继 #1002 反思里"总宽度会掩盖左右一多一少"之后，同一主题（弹性 glue 的三项参数与实际断行）下的第二个具体反例，应该合并进已有的相关经验条目。
- "调用处写宏 vs 写字面正文"的区分目前只留在这份反思和测试文件注释里，没有进入 `coding-conventions.md` 或 fntef 相关的架构文档，后续再有类似 issue 容易重新踩这条既有限制当作新缺陷去修。

## Promotion Candidates

- **正文经宏参数间接展开会让内部装饰盒固化收缩量，无法归纳为「用户没按预期方式调用」。** ulem／fntef 等自行扫描正文并切片装盒的机制，只应对正文使用字面记号；确需重排某种特殊语法（如公式尾＋空格）时，应该用条件判断只对该语法走重排路径，其余情况保持字面展开，不能为了少数情况把全部正文都改成间接展开。
- **量弹性 glue 的收缩量是否真的能参与断行，不能只用单个 `\hbox`／`\vbox` 包起来测；必须放进 document 主垂直列表里真正跑一次断行。** 这是对已有"弹性 glue 的三项参数与实际断行"教训的补充反例，建议在 `lessons-learned.md` 对应条目里追加这一具体反例说明。
- **子系统标签和现象所指的位置，不能代替 bisect 定位真正的引入提交。** 相关 issue 之间即使表面现象相似（同为 fntef 装饰、同为换行相关），引入点也可能落在完全不同的历史提交里；排查顺序应该是先 bisect 确认引入点，再去读对应提交的决策文档，不要反过来。
- **调用处用字面正文 vs 用宏承载正文，是两条不同的收缩链路，测试必须明确区分并分别验证。** 用宏承载正文触发的是已知既有限制，不应该混进本次缺陷的验证范围。

## Follow-up

- 若后续要修复"正文经宏参数传入导致收缩量丢失"这条既有限制，需要新开 issue；本次修复的范围明确不含它。
- recorder 后续同步 `xecjk-architecture.md` 时，补充 ulem 集成层"正文必须字面记号、不能经参数间接展开"这条约束，并关联本反思与 #1002 的 `math-space` 逻辑，说明两者的分工边界（#1002 只解决"公式尾＋空格"这一种需要重排的情况，其余场景必须保持字面）。
