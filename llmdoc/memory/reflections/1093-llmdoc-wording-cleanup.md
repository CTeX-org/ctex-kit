# 反思：#1093 全库修订 llmdoc 措辞

## 任务

用户要求修订 `llmdoc/` 中不符合中文习惯的措辞，例如“实装、落地、形态、当场、同款、拍板、守住、闸门、对拍、真接入、真启用”。最终改了 108 个文件，709 行增、709 行删。CI 通过，Bot 审查结论为 APPROVE。

## 做法

- 先把规则写成 `./tmp/wording-guide.md`：必改词、单字“盒”改为“盒子”、“真……”一类强调词及保留条件，以及不能改的内容（代码、路径、引用原文、被锚点引用的标题）。
- 按行数把 145 个文件平均分成 6 组，交给 6 个并行子代理通读修订。
- 主代理集中收尾：用 `sed` 统一“合同→契约”“零判别力→没有判别力”“## 促进候选→## 可写入稳定文档的内容”“已促进→已写入”；再派一个子代理按语义逐处处理 79 处“门禁／门控”，分别改成检查、校验或条件判断。

## 预期与实际

- 预期：6 组各自按指南改完，合并后全库用词一致。
- 实际：指南点名的词各组改得一致；指南没有点名的边界词各组判断不同，需要额外一轮集中收尾。

## 问题

- “门禁”“门控”有的组改了，有的组保留。
- “合同”（contract）、“促进候选”、“零判别力”、“镜面”等词，各组都因为“只改本组会和其他组不一致”而没有改。每个分片单独看都合理，合起来就是全库都没改。
- 子代理用「」转述其他文档的标题时，转述内容要和对应组改后的标题一致，例如 #1026 的“片段盒内”标题、xecjk-architecture 的“参数形态区分”标题。分片之间看不到彼此的改动，这类交叉引用只能在合并后检查。
- 有些子代理在报告中把仓库路径写成另一个用户目录，实际改的是正确的仓库。报告里的路径不能直接当作事实。

## 根本原因

- 指南只列了明确要改的词，没有预先列出“跨文件高频、可改可不改”的边界词并给出统一决定。并行分片缺少全局视角，遇到边界词时，最稳妥的选择就是保守不改。
- 标题改名会影响其他文件里的转述，但分片是按行数切的，不是按引用关系切的。

## 有效的验证方法

- 不变量检查：逐文件比对修改前后排序后的行内代码、`[[wiki 链接]]` 和 Markdown 链接目标集合。纯措辞 diff 不应改变这些集合。本轮只有一处差异，是有意把“门禁”写成 `l3build check`。
- 另跑 `git diff --check`，检查空白错误。
- 这种检查成本低，能在不逐行复读 1400 多行 diff 的情况下，确认代码、路径和链接没有被误改。

## 可写入稳定文档的内容

- 可写入 `guides/`（如果将来新增文档维护指南）：并行分片修订术语前，先用 `grep -c` 统计候选词的跨文件出现次数，把高频边界词列进指南并逐个给出“改成什么／保留”的决定；标题改名要在指南中列出新旧对照，供转述引用的分片使用。
- 已写入 `reference/doc-terminology.md`：本轮定下来的跨文件替换决定（契约、PR 检查／条件判断、盒子、没有判别力、小节名），以及纯措辞修改的不变量检查方法（行内代码、wiki 链接、Markdown 链接目标集合前后不变，加上 `git diff --check`）。
- 只保留在 memory：本轮具体的词表和 79 处“门禁／门控”的逐处取舍。仓库规则已经写明主要禁用词，词表细节不必进入稳定文档。
- 只保留在 memory：子代理报告路径有误属于工具层现象；对应的做法是“子代理报告里的路径和结论要自己核实”，可以考虑并入已有的协作经验，但不单独成文。

## 后续

- 下次做全库措辞修订时，第一步先统计边界词并写进指南，再分片。
- 如果维护者认可不变量检查方法，可以把比对脚本整理到 `scripts/` 或写进文档维护指南，下次直接使用。
