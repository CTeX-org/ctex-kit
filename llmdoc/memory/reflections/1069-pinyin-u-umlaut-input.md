# 反思：#1069 拼音参数直接输入 `ü`

## 报告的提问方式

报告者没有直接说「这里有 bug」，而是问「文档这么写，我这么用却不行，是文档该改还是我用错了」。他给了 MWE 和截图：`\pinyin{nv3}` 得到 `nǚ`，`\pinyin{nü3}` 排出字面的 `nü3`。

这个提问方式本身值得注意：他从手册那句「为了输入的方便 `ü` 可以用 `v` 代替」推出「那么直接写 `ü` 也应当能用」。这个推断是对的——「为了方便可以用 A 代替 B」的自然读法就是「B 本身也能用」。所以两个选项里（改文档 / 改实现），正确答案是改实现。

## 同一个缺陷在两条引擎路线上症状不同

这是本任务最该记的一点。我先在 XeTeX 下复现，看到的是「输出错误」；顺手试 pdfTeX + CJKutf8 才发现那边是**编译直接中止**：

- XeTeX：`ü` 不在声调落点表里（`\c_@@_v_tl` 这一组常量只覆盖 ASCII 字母），`\@@_pinyin_aux:n` 认不出它是元音，整个音节走「原样输出」分支，声调数字也不会被去掉 → 字面的 `nü3`。
- pdfTeX/CJKutf8：`ü` 是两个字节，逐记号取到的是半个字符，拿它做 `` `#1 `` 求值时报 `Improper alphabetic constant`，随后又有十几个连锁错误，退出码为 1。

如果只按 issue 里的截图（XeTeX）修，我会把它当成「一处输出不对」，严重性评估偏低，而且不会想到去测 pdfTeX 那条路线。**xpinyin 支持两条引擎路线，任何输入层面的缺陷都要在两条路线上各复现一次**——这条其实已经写在 `build-and-test.md` 里（两套互不复用的适配层），但我此前理解成「测试要覆盖两条路线」，没理解成「诊断也要在两条路线上各做一次」。

## 第一版修法让 pdfTeX 路线直接加载失败

我的第一反应是给 `ü` 补两张表的条目：`\tl_const:Nn \c_@@_ü_tl { 1 }` 加 `\cs_new_protected:cpn { @@_num_to_tone_ü:Nn }`。XeTeX 下完全正确，实测 `nü3` → `nǚ`、`jü4` → `jǜ`。

然后 pdfTeX 下宏包**一加载就失败**：`! LaTeX Error: Invalid UTF-8 byte "BC`，报在 `\tl_const:Nn \c__xpinyin_ü` 这一行。控制序列名里含非 ASCII 字符，在 pdfTeX 上根本写不出来。

改为在入口折叠（用 `\tl_replace_all:Nnn` 把 `ü`→`v`、`Ü`→`V`）之后，两条路线都恢复了正常。关键事实是 `\tl_replace_all:Nnn` 匹配的是**记号序列**：pdfTeX 下 `ü` 是 2 个记号，替换式里的 `ü` 也是同样 2 个记号，照样匹配得上（实测 `nü3` 是 4 个记号，替换后与 `nv3` 逐记号相同）。折叠之后包内其余逻辑一处都不必改——声调落点、`\@@_replace_v:n` 的 `l`/`n` 判断全部复用。

教训不止「别用非 ASCII 控制序列名」这么窄，而是：**在多引擎包里，凡是要把用户输入的字符搬进标识符（控制序列名、`\csname`、变量名）的方案，都要先问这个字符在最弱的那条引擎路线上是什么**。改为在数据层做规范化，通常能避开这一整类问题。

## 折叠后的值泄漏到回退路径（我自己引入的回归）

折叠版本第一次运行后，`\pinyin{nü}`（无声调数字）输出 `nv`——基线是 `nü`。原因是我把 `\l_@@_save_tl` 也设成了折叠后的值，而它正是「整段输入里没有声调数字」时的回退输出。

这类问题的共性：**做输入规范化时，要清点「规范化后的值」会流到哪些出口**。只有参与计算的那条路径可以安全地使用折叠后的值；凡是会把输入原样回显给用户的出口，都得用原始值。我当时只想着「后面的循环要用折叠值」，没想到还有一条回显路径。

## `Ü→v` 变异第一版全绿

补测试时我为「`Ü` 折成 `V` 而不是 `v`」写了断言，用的是 `\pinyin{Nü3}`。变异（把 `Ü`→`V` 改成 `Ü`→`v`）跑出来**全绿**。

原因很简单：`Nü3` 里的 `ü` 是**小写**，走的是 `ü`→`v` 那条规则，根本碰不到 `Ü` 那条。我写的是「大写声母 + 小写 ü」，而要测的是「大写 Ü」。补上 `\pinyin{NÜ3}` 与 `\pinyin{NV3}` 的对照后，同一变异只让这一项变红（2 行）。

仓库已有的规则「新增测试项后要检查它是否真的经过被断言的那条路径」在这里又出现了一个实例。但这次的情况比之前更隐蔽：断言的名字（`N-umlaut-3`）、注释（「大写声母：Ü 折成 V」）看起来都对得上，只有输入里的那个字符不对。**注释声称测的是哪条规则，不等于输入确实会走到那条规则**——检查方式是问「如果这条规则不存在，这个输入的结果会变吗」。

顺带发现全大写输入（`NV3`、`HAN4`）本来就排不出调号，是既有限制（声调落点表只有小写元音），已写进手册。

## 又一次把 DIFF 写进了基线

多音节那一项，我用来给出预期结果的 oracle（对照写法）是手工拼写的字面重音 `n\v{\"u}h\'aizi`，而 `\pinyin` 会在音节之间插 `pysep`（缺省一个空格），宽度必然不等。`l3build save` 照样把 `wd=DIFF 43.30566 vs 36.94824` 存进了 `.tlg`——一个「预期为失败」的基线。

我是在 save 之后 grep 基线内容时看到的。**`l3build save` 之后必须读一遍新基线里自己那几行**：它不会因为断言结果是 DIFF 就拒绝保存。这一条仓库里已有记载（#1037 的「无 Overfull」那次），我仍然又犯了一次。

修正办法是换判据，而不是修改 oracle：这一项要断言的本来就是「两种写法结果相同」，直接对比两条 `\pinyin`（新增 `\CmpPinyinPair`），比与手工拼写的字面形式对比更切题，也不必去照搬 `pysep` 的空白。**当 oracle 需要照搬被测实现的细节时，往往说明判据选错了。**

## 工作目录被重置，改动写到了副本上

`\setpinyin` 那处修改，我的 heredoc 脚本执行后 assert 通过、打印「已改」，但 `l3build unpack` 出来的 `.sty` 里完全没有改动。

原因是 shell 的工作目录在两次调用之间被重置到了仓库根，而仓库根下恰好有一个 `xpinyin.dtx`——那是我更早一次在错误目录下执行的命令留下的副本。于是 assert 在那个陈旧副本上匹配成功、写入成功，实际的 `xpinyin/xpinyin.dtx` 一字未动。

两个教训：

1. **改完文件要看产物，不是看脚本的输出。** 我信了脚本打印的「已改」。可靠的判据是 `grep` 生成的 `.sty`／`.def`。这与「变异实验后要确认变异真的进了产物」是同一条，只是这次发生在正常修改而非变异上。
2. **脚本里用绝对路径，或者开头显式 `cd`。** 依赖「上一条命令留下的工作目录」不可靠。这次还在仓库根留下了一个未跟踪的陈旧 `xpinyin.dtx`——如果没注意到 `git status` 里那行 `?? xpinyin.dtx`，它可能被一起提交，成为一份与实际源码不同步的多余副本。

## 顺带修的第三处

测查询命令时发现：`\setpinyin{女}{nü3}` 之后 `\xpinyinvalue{女}` 在 `tone=number` 下返回 `nü3`，而查询表通篇用 `v` 记 `ü`（`xpinyin.lua` 生成时即如此），`number` 形式的设计目的就是能直接作为 `\pinyin` 的参数使用。原样存 `ü` 会让同一张表里出现两种拼写。

这是 #550 那次「`\setpinyin` 要同时改两张表」的延续：那次修的是「有没有写」，这次修的是「写进去的拼写规范」。**一个值要存进两处时，除了「都写了」还要问「两处的规范化约定是否一致」。**

## 独立盲审的唯一发现：我又写了一个会过时的具体数字

盲审（在网络隔离的快照上进行，审查者看不到之前的对话）的结果是 0 个阻塞、0 个重要、1 个小问题，唯一那条是：`build-and-test.md` 里「去掉折叠后 `pinyin-tone01` 红 24 行」这个数字不对，他实测 26 行（13 个断言 × 2）。

我复算得到的是 24（12 个断言 × 2）。差异出在 `NU-umlaut-caps` 那一项：它断言 `\pinyin{NÜ3}` 与 `\pinyin{NV3}` 相等，而在「去掉 `ü`→`v`」这个变异下 `Ü`→`V` 仍然生效，两侧同为字面 `NV3`，**按设计就不该变红**——它是 `Ü`→`v` 那个变异的判据，不是这个。所以他把它算进「应变红」得到 13，我按实际变红得到 12。

结论不是「他算错了」，而是**这个量本身不该被记录**：两个数在各自的统计方式下都成立，而 diff 行数还随呈现方式变化。改成「TEST 4／5 的 12 个断言全红」之后就没有歧义，也不会因工具不同而变化。cjkutf8 那侧同理，改为「因编译中止导致整个基线失配」而不是「红 190 行」——虽然他复核后确认 190 这个数完全准确。

这是本任务里我第二次因为写具体数字而给出会过时的断言（前一次是 #550 那批，已记过五次）。规律很清楚：**凡是「我跑一遍得到的数」，写进文档前要先问它依赖什么。依赖工具呈现方式或统计方式的，一律换成结构化描述。**

补记：原审查者在补充说明（supplement）里还留了一条「仅留痕、不需处置」的观察——我订正 tone01 那个数的同一句里，cjkutf8 侧仍写着「`^!` 行 190」，与这一节自己给出的「不要写成 diff 的确切行数」相矛盾。他判断风险低（那个数带有「编译中止致整个基线失配」的定性，不会被误当成覆盖数量），所以不要求处置。我仍然改了：**一段文字里同时给出规则和违反该规则的示例，后来者会无法判断哪个才是要遵守的**。现在两侧都按结构描述写，规则与示例一致。

还有一点与统计方式有关：他的 26/13 与我的 24/12 不一致，根源不是谁数错，而是两人做的变异不是同一个——他删整个折叠块（`Ü`→`V` 也删了，于是 `NU-umlaut-caps` 会红），我只删 `ü`→`v`。**报告变异结果时要写清「改了哪一行」，否则同一句「某某变异下红 N 项」在不同人手里对不上。**

## 补记一：删 MAINTAINING.md 时按标题清点，漏了引言段

任务收尾后被要求删掉 `xpinyin/MAINTAINING.md`。我按 `grep '^## '` 列出 5 个小节逐一判断去留，判定 4 节冗余、1 节（xeCJK 未文档化内部接口清单）必须保留并迁进 `package-architecture.md`，然后删掉整个文件。

漏掉的是文件开头 H1 标题下的那段文字，它不属于任何 `##` 小节，内容是：xpinyin 的 PR 以 `xpinyin/maintaining` 为合入目标，以及维护权变更的时限安排（2026 年 9 月底）。全仓检索确认那里是这些信息**唯一**出现的地方。PR 上的自动审查以 REQUEST_CHANGES 指出了这一点，经核实属实。

两个教训：

1. **按标题层级清点会漏引言段。** `grep '^## '` 给出的是小节列表，H1 之后、第一个 `##` 之前的内容不在其中。清点文件内容应当核对行数覆盖（各节行数之和是否等于文件总行数），而不是罗列标题。
2. **按读者决定去向，而不是按「内容是否重复」。** 我判断那 4 节「冗余」的依据是「llmdoc 或 dtx 注释里已有」，但漏掉的那段面向的是**贡献者**，而 llmdoc 只有维护者会读——即便内容不重复，放在 llmdoc 里也等于丢失。这段最终放进了 `README.md` / `README-en.md` 的「参与贡献」一节，那才是它本来就该在的位置（原先放在只有维护者会看的 MAINTAINING.md 里，本身就放错了地方）。

## 补记二：rebase 到 master 时自动合并把索引行复制了十几遍

分支要 rebase 到 master（53 个提交，两侧都改过的 llmdoc 文件有 6 个）。冲突集中在 `llmdoc/index.md`——那是个每行动辄数千字的索引，两侧各自在同一行末尾追加了不同内容。

我写了个「追加型自动合并」脚本（公共前缀 + HEAD 侧追加的部分 + incoming 侧追加的部分），放进 `rebase --continue` 的循环里执行。**它对单次冲突是正确的，但在循环里，每一轮都会把我这一侧追加的内容再接一次。** 结果：

- `build-and-test.md` 那行：同一段追加重复 7 次，12939 字
- `lessons-learned.md` 那行：重复 16 次，20489 字（应有长度的 4.5 倍）
- `package-architecture.md` 那行：`xpinyin -> xeCJK` 说明重复 3 次，且**第一份仍指向已被我删掉的 `xpinyin/MAINTAINING.md`**

CI 全绿——这些都是说明文字，不参与编译，任何测试都看不见。是 PR 上的自动审查作为小问题指出来的（它注意到「同一条说明写了三次，第一次还是失效链接」）。

修正办法不是继续打补丁，而是**三方重建**：取 merge-base 的版本，算出 master 相对它追加了什么、我相对它追加了什么，再分别拼接上去。长度回到 8272／4269。

两条教训：

1. **在 `rebase --continue` 循环里跑自动合并脚本，要保证它幂等**。我的脚本每次都以「当前 HEAD 行」为基准，而当前 HEAD 行已经包含上一轮接上的追加内容，于是不断累积。基准应该取 merge-base，而不是不断变化的 HEAD。
2. **纯文字文件的合并错误，任何自动检查都拦不住**。代码合坏了测试会红，`.tlg` 合坏了基线会红，而索引行重复十六遍照样 CI 全绿。这类文件合并后必须显式扫描重复子串——我现在把「以 40 字左右的粒度扫描全文件」当作固定的收尾步骤。

这次还暴露出一类脚本无论如何都判断不了的情形：我这一侧和 master 各自追加的内容里都有同一条「LaTeX2e 命令钩子机制」规则，属于实际的内容重叠，只能人工决定保留哪份。

## 补记三：我给 `\setpinyin` 补的那处同步，条件判断选错了判据

rebase 之后 PR #1051 上的自动审查提了一个**阻塞问题**，指的正是本任务加的那段代码。经核实属实。

我当时写的判断条件是「该字的查询控制序列已存在吗」：

```latex
\cs_if_exist:cT { c_@@_query_ \@@_char_to_unicode:n {#1} _tl }
```

理由是「查询表没载入时不该多设控制序列，否则会让『表没载入』的判据失效」——这个理由本身是对的，我还专门写进了注释。但判据选错了：它同时排除了**数据库未收录的汉字**。实测 `\setpinyin` 对 U+5159 只更新注音表，随后 `\xpinyinvalue` 仍报 `No pinyin reading`，与手册那句「注音与查询给出的首选读音始终一致」直接冲突。

而补录生僻字读音**恰恰是 `\setpinyin` 最典型的用途**——收录了的字本来就有读音，用户最需要手工指定的正是表里没有的那些。所以我漏掉的不是一个边角情形，而是这个接口的主要用例。

改用 `\g_@@_query_loaded_bool`（「查询表载入了吗」）之后，两个目标同时满足：未载入时仍不设置（原来的判据仍然有效，实测仍正确报「表没载入」），未收录时会**创建**查询项。

一般化的教训：**往第二张表回写时，判断条件应当问「那张表可用吗」，而不是「这一条已经存在吗」。** 后者把语义从「创建或覆盖」悄悄缩成「只覆盖」。#550 那次修的是「有没有写第二张表」，#1069 修的是「写进去的拼写对不对」，这次修的是「什么条件下才写」——同一处代码的第三种错误。

补的回归用例（`pinyin-query01` 末尾，U+5159）判别力已实测：把判断条件改回 `\cs_if_exist:cT`，那三行 `shí` / `sh` / `shi2` 被 `No pinyin reading` 取代。

顺带一个小问题：我最初在 `.dtx` 注释里直接写了那个生僻字举例，`l3build doc` 的缺字形计数从 0 变成 2（手册字体 `FandolFang-Regular.otf` 没有该字形）。测试文件里用它没问题（`.tlg` 记录的是节点），但手册要发布给用户，改成码位描述后回到 0。

## 补记四：同一处代码的第四种错误（轻声 `5`）

修好判断条件之后，同一轮审查又提了一个阻塞问题，还是这段回写查询表的代码：`\setpinyin{兙}{shi5}` 之后 `tone=none` 的 `\xpinyinvalue` 返回 `shi5` 而不是 `shi`。

经核实属实。依据是三份互相印证的证据：

- 生成侧 `xpinyin.lua` 的 `numbertable` 只产出 `1`--`4`，轻声不给数字；
- 生成的 `xpinyin-query.def` 里带 `5` 的条目**为零**；
- 读取侧 `\@@_query_base:nn` 用 `` `#1 < `5 `` 判断，只把 `1`--`4` 当声调。

也就是说查询表的约定是「轻声不写数字」。而手册那句「声调用音节末尾的数字 1--5 表示（5 是轻声）」说的是 `\pinyin` 的**输入**约定——**两个约定不同**。我回写时遵循的是手册里的输入约定，应当遵循查询表的约定。

所以这一处代码我连错了四次，每次都是「回写第二张表」的不同侧面：

| 轮次 | 错在哪 |
|---|---|
| #550 | 根本没写第二张表 |
| #1069 | 写了，但 `ü` 没折成 `v` |
| PR #1051 第一条 | 判断条件问「这条已存在吗」，漏掉未收录的字 |
| PR #1051 第二条 | 轻声 `5` 没去掉 |

**共同的失误模式**：我每次都只核对了「最显眼的那一条约定」，就认为规范化已经完整了。正确做法是把目标表的编码约定逐条列出来核对——而且要以**生成侧实际产出**为准，不是以文档措辞为准（文档那句「1--5」恰好会把人引向错误方向）。

实现上还出过一个小错：第一版用 `\str_range:Vnn`，不存在该变体，`Undefined control sequence`。改成先展开再传 `\str_range:nnn` 的辅助函数。这也提醒我注释要跟着实现改——第一版注释说「用 `\tl_if_in:nnTF` 先筛一遍」，重写后那步已经没有了，若不改，注释就与实现不符。

## 补记五：升级式解包与发版校验（PR #1051 第三轮）

同一轮审查的第三批，两条指出的都不是我这次改的代码，而是 #550 引入、一直没被发现的缺口。

**阻塞：升级式解包会直接失败。** `.ins` 里 `if not kpse.find_file("xpinyin.db")` 仍只检查一个 db，而 #550 起生成器同时产出 `xpinyin-query.db`。在**以前解包过 xpinyin 的目录**里升级时，旧 db 让生成器被跳过、新 db 不存在，docstrip 以 `! Cannot find file xpinyin-query.db` 退出（实测退出码为 1）。改为任一缺失都重建。

这条路径 **CI 在结构上覆盖不到**：`unpack_prehook` 首句就是 `cleandir(unpackdir)`，永远从干净目录开始。所以我没有勉强加一个用例，而是把手工复现步骤和这个覆盖缺口写进 `build-and-test.md`——承认缺口比假装覆盖了更有用。

**重要：发版校验少核对一个版本槽位。** `xpinyin-query.def` 有第三个 `[<日期> v<版本>]` 槽位，共享的 `update_tag` 用通用模式匹配，已经会回写它（所以 `l3build tag` 一直幂等），但 `release.yml` 只单独提取并核对两处。补了 `QUERY_VER`，两种失败情形都验证过：改成 `v9.9` 时 `STAMP_VERS` 出现 2 种、删掉整行时 `QUERY_VER` 为空，按 fail-closed（取不到值就判为失败）中止。

**排查过程中我连续犯了三次同一类错误**，值得单独记：

1. 手工用正则截取 `.ins`，只取到 install 段的**第一块**，漏了含 `\endbatchfile` 的第二块 → `File ended while scanning use of \generate`；
2. 补第二块后仍缺 `\input docstrip` 引导 → 另一个无关的 `Emergency stop`；
3. 最关键的一次：改完 `.dtx` 后**没重跑 `l3build unpack`**，测试用的还是旧 `xpinyin.ins`（里面还是只检查一个 db），于是得到「修复无效」的错误结论，我差点去改生成器。

三次都是「我手上那份生成物不是新的／不是完整的」。改用仓库生成的 `.ins` 之后，才得到可靠的结果。**复现涉及生成物时，第一件事应当是确认那份生成物就是当前源码的产物。**

还有一处是我自己制造的弯路：我给那段 `\directlua` 加了四行 `--` 中文注释说明修复理由，结果 \TeX{} 把实参折成一行后，`--` 把后面整个 `if` 都变成了注释，生成器静默不执行，**症状与完全没改一样**。能识别出这一点的信号是 `xpinyin.db` 的 md5 没变——说明生成器根本没跑，而不是跑了没写全。把注释移到 `.dtx` 这一层后问题消失。
