# 反思：xpinyin/maintaining 的 rebase、措辞修订与 Unihan 18.0 数据变化

## 任务

- 把 `xpinyin/maintaining`（57 个提交）rebase 到 master `ef49ca4e`。master 比分支多 23 个提交，其中包括 #1093 的全库措辞修订。
- 修订分支相对 merge-base 新增的文字（llmdoc、代码注释、`.dtx` 手册正文和 `\changes`）中不符合中文习惯的措辞。
- 处理推送后三个平台 `test-xpinyin` 同时失败的问题（PR 自动审查列为阻塞问题）。
- 收尾：修正维护者邮箱，删除 README 中集成分支的临时说明。
- 最终 CI 全绿，审查结论为 APPROVE，没有遗留问题。

## 预期与实际

- rebase：预期冲突可以按 #1069 的教训三方重建。实际上冲突全部出现在 llmdoc 的超长行里：master 改了措辞，分支在同一行追加了内容，逐行三方合并无法处理，需要改成按词合并。
- 措辞修订：预期子代理按指南改完即可。实际上指南列为必改的“口径”“坑”被 3 个子代理以“master 上大量保留”为由保守不改，主代理集中收尾时又统一替换了 20 多处。
- 测试失败：起初以为是 rebase 或措辞修订引起的。实际原因是上游 Unihan 数据从 17.0 更新到 18.0，与本分支的改动无关。

## 问题

1. **词级三方合并。** 冲突块按词切分（每个词一行）后交给 `git merge-file` 三方合并（脚本 `/tmp/wmerge.py`，未保存进仓库）。两侧在同一位置各插入一行时，脚本改为“按行首反引号路径配对，再逐行按词合并”。只有一处需要手动处理：分支把 `build-and-test.md` 的 cjkutf8 条目上移并改写，上移后的行也要采用 master 的措辞。`sync.md` 的冲突一律取被重放的一侧，结束后单独提交，把 watermark 指向改写后的提交。
2. **修残缺文字前先确认是谁引入的。** 措辞子代理报告 `index.md` 有 4 段残缺文字。先用 `git show origin/xpinyin/maintaining:llmdoc/index.md` 对照，确认 rebase 前就已存在，是更早一次脚本替换失败留下的，不是本次解决冲突时引入的。
3. **子代理不执行指南里的决定。** 指南已经把“口径”“坑”列为必改，子代理仍以“和其他文件保持一致”为由保留，其中一个把“口径”改成“统计口径”。这与 #1093 的现象相同，但这次指南已经给出了决定，说明只写“必改”不够。
4. **标题和被转述原句的旧文本检查。** 第一次取旧文本的前 24 个字符做前缀匹配，结果全部是命中新标题自身的误报。改成用完整旧文本精确匹配、排除未改动的加粗句后，只剩 2 处真实残留（两份 997 文档仍用“整支重选被跳过”的旧说法），已同步。
5. **`doc-terminology.md` 给的不变量检查正则有缺陷。** `` `[^`]+` `` 遇到用双反引号包住的行内代码（例如 ``` `` \` `` ```）会配错对，产生大量误报。两个子代理各自发现了这个问题，主代理自己写的第二版正则也仍有误报。最后用子代理写的脚本：按行扫描，按反引号串的长度配对开始和结束位置。结果只剩 3 处有意修改的差异。这个脚本没有保存进仓库。
6. **子代理顺带发现的事实错误要逐条核实。** 子代理修正了多处由本分支引入的事实错误，主代理逐条对照源文档、代码和提交记录后才保留：
   - `cjkutf8-01.lvt` 注释里“TEST 7 仍会通过”应为 TEST 6（已核对 TEST 6 的每次比较都在独立的 `\hbox_set:Nn` 里）；
   - “变异 C”按原提交 `67a33c6f` 的说明确实是全局赋值变异；
   - #1069 反思里“服从了前者，应当服从后者”写反了；
   - `index.md` 的 997 条目前半句仍在陈述已经撤回的结论；
   - lessons-learned 写“连错三次”，反思和 4 个修复提交（`9d48b723`、`1340e326`、`68f4f8ff`、`a7f999be`）都表明是四次；
   - #265 决策引用的规则标题实际在 `xecjk-architecture.md`；
   - 两处 `.dtx` 注释与代码不符：`\@@_query_get:n` 本身不检查条目是否存在，由调用方检查；查询表只在 XeTeX 下载入。
7. **子代理报告里的仓库路径与实际不同。** 所有子代理都报告了错误的路径，与 #1093 的现象相同，实际修改的是正确的仓库。
8. **Unihan 18.0 使测试失去数据载体。** `pinyin-query01` 第 5d 项用「噷」覆盖查询表里的 hm 条目（整体鼻音，声母为空、hm 整体作韵母）。数据库按 kMandarin > kXHC1983 > kHanyuPinyin 的顺序取首选读音；「噷」的 kMandarin 在 17.0 是 hm，18.0（2026-07-31）改为 xīn，首选读音随之变成 xin1。CI 每周下载最新的 `Unihan.zip`（`_test-package.yml` 的 weekly cache key），本机构建时也重新下载了最新版。
   - 排除本分支的影响：用 rebase 前的旧分支在同一环境运行，去掉时间戳后 diff 逐字节相同。
   - 用户最初选择刷新基线。扫描 18.0 数据后发现，首选读音为 hm 或 hng 的字已经一个都没有，只剩 m、n、ng。刷新基线会让“hm 整体作韵母”这条规则失去覆盖。把这一信息告诉用户后，改为在测试里用 `\setpinyin{噷}{hm5}` 写进查询表，`.tlg` 不变。
   - 注释起初写成“hm 来自 kXHC1983”，拿到另一份 17.0 数据后才发现 17.0 的 kMandarin 本来就是 hm，已更正。
   - 验证：分别放入 17.0 和 18.0 的 `Unihan.zip`，清空 `build/` 后运行 `l3build check`，两次都是 9/9；再查生成的 `xpinyin-query.db` 中 U+5677 的值，分别是 hm 和 xin1，确认两次确实用了不同的数据。
9. **推送与 CI 跟踪。**
   - rebase 后强推需要 `CTEX_PREPUSH_ALLOW_FORCE=1 git push --force-with-lease`，带这个环境变量的命令被权限分类器拒绝，由用户在输入框里自己运行。
   - `make check-pr-ci` 发现任何检查失败就立即退出，不等 Codex 审查结束，需要另写轮询，等审查检查结束后再读评论。
   - 一次普通 `git push` 因 hook 等待 CI 超过工具的 10 分钟限制而被中断，但推送本身已经成功；之后改为在后台运行 `make check-pr-ci`。
10. **提交前的一致性检查。** 用户新增的维护者信息里，作者栏把李清的邮箱写成 `qinglee@gmail.com`（GitHub 用户名），与版权行的 `sobenlee@gmail.com` 不一致。询问用户后改回。删除 README 中集成分支的临时说明前，先确认“两条测试路线”的说明已经在 `build-and-test.md` 里，再把 llmdoc 中“这些内容迁入 README”的两处说法改为“已删除”。

## 根本原因

- 按行的三方合并假设两侧改的是不同的行。超长行把整段内容放在一行里，master 的措辞修改和分支的追加落在同一行，只能按词合并。
- 并行子代理只看到自己那一组文件。它们看到 master 上大量保留某个词，就把“与全库一致”看得比指南的明确决定更重要。指南没有写清“即使 master 上还有，本分支新增文字也要改”。
- `doc-terminology.md` 里的正则只按单个反引号配对，没有考虑 CommonMark 中用多个反引号包住含反引号的代码的写法；写入稳定文档时没有在含这类写法的文件上测过。
- 测试用一个具体汉字的数据库读音来承载一条与具体汉字无关的切分规则。上游数据一改，被测规则的输入就没了。`Unihan.zip` 不固定版本，这类依赖在本地和 CI 上都会出现。
- 注释里关于数据来源的说法（kXHC1983）是推断出来的，没有对照当时版本的数据。

## 缺少的文档或信号

- `doc-terminology.md` 缺少本次定下的替换：口径、确数、证否、坑／踩坑、形态（在“失败方式”一类语境下）。
- `doc-terminology.md` 的检查正则需要换成能处理多反引号行内代码的方法；也没有写明“标题改名后用完整旧文本精确匹配检查残留”。
- `build-and-test.md` 只写了 `Unihan.zip` 使用 weekly cache key，没有写明它不固定版本、每周取最新，以及断言具体汉字读音的用例会随上游数据变化。
- 措辞指南模板里缺少一句明确的话：“列为必改的词，即使 master 上仍大量存在，本次范围内也要改；不得以一致性为由保留。”

## 可写入稳定文档的内容

- **`reference/doc-terminology.md`**（建议写入）：
  - 在替换表中补充：口径 → 统计方式、计数方式、说法；确数 → 确切数字；证否 → 推翻、否定；坑、踩坑 → 问题、容易出错的地方、失误；表示“失败的样子”的“形态” → 失败方式；其他语境下的“形态” → 写法、形式。
  - 把不变量检查中的 `` `[^`]+` `` 换成按行扫描、按反引号串长度配对的方法。建议把脚本放进 `scripts/` 或直接写进文档，并用含 ``` `` \` `` ``` 的文件测试一次。
  - 补一句：标题或被转述的原句改名后，用完整旧文本在全库精确匹配，排除原文本身未改的位置；不要用前缀匹配，前缀会命中新标题自身。
- **`memory/lessons-learned.md` 新开一条**（建议写入）：上游数据变化使被测规则失去数据载体时，不刷新基线，也不等上游恢复，而是用受控输入（这次是 `\setpinyin`）固定被测值；然后分别用新旧两版数据各跑一次，并检查生成物，确认两次确实用了不同的数据。这是已有条目「刷 `.tlg` 基线前先按上游根因分类」之外的第三种处理：那一条回答“刷不刷”，这里的情况是刷新后测试就不再覆盖原来的规则。另附一个次要教训：注释里关于数据来源的说法要对照当时版本的数据核实。
- **`memory/lessons-learned.md` 已有条目「rebase 冲突里双方各自在同一长行追加要按三方重建」**（建议补充实例）：本次两侧的改动不只是追加，还有 master 对同一行的措辞修改，所以改用按词切分后交给 `git merge-file` 三方合并；两侧在同一位置各插入一行时，按行首路径配对后逐行按词合并。合并后按词核对原提交新增的片段都在结果里。另外，修残缺文字前先用 `git show <rebase 前的分支>:<文件>` 对照，确认残缺是否是本次引入的。
- **`reference/build-and-test.md` 的 Unihan 缓存说明**（建议写入）：`support/Unihan.zip` 不固定版本，CI 按 weekly cache key 每周下载最新版，本地构建也会重新下载；断言具体汉字读音的用例会随上游数据变化。要测的是规则而不是某个字的收录读音时，应当用 `\setpinyin` 固定输入。
- **只留在 memory**：
  - 子代理以“一致性”为由不改指南列为必改的词。对应做法（在指南里写明“即使 master 上仍有也要改”）属于措辞修订流程，等将来有文档维护指南时再考虑写入 `guides/`。
  - 子代理报告的仓库路径错误（#1093 之后第二次出现），以及子代理顺带修正的事实需要主代理逐条核实。
  - `make check-pr-ci` 在检查失败时提前退出、不等审查结束；强推所需的环境变量被权限分类器拒绝；`git push` 超过工具时间限制但推送已成功。这些是工具和环境层面的现象。如果 `check-pr-ci` 提前退出的问题再次出现，可以考虑写入 `guides/push-and-pr-review-workflow.md`。
  - 维护者邮箱不一致、删除 README 临时说明前确认内容已有去处，这些是本次的具体处理。
