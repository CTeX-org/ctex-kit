# 反思：#1067 花括号使 ulem 片段盒吃掉 ecglue 收缩量

## 任务

Issue #1067 报告 `\CJKunderline{虚室 {hello} 生白}` 里的花括号使该处中西文间距
（`\CJKecglue`）的可收缩量失效。任务是判断根因并处置。

## 结论

这是 `ulem` 切分正文方式带来的既有限制，不是本包这次才引入的缺陷。自然宽度不受影响
（四种写法都是 67.22pt），因此只在 `\hbox to` 一类固定宽度且收缩吃紧的场合才会显现；
段落断行下两种写法都不溢出，视觉上看不出差异。

只在工作树 v3.10.5 复现：系统安装的 v3.10.4 下两行溢出量相同（均 4.22pt），v3.10.5 下
分化为 2.0pt 与 3.11pt。

影响范围比 issue 原报告更广（判据是压窄 2pt 后的 `\badness`，73 表示收缩量够用，
1000000 表示不够）：

- 受影响：`虚室 {hello} 生白`、`虚室 \textbf{hello} 生白`、`虚室 {文字} 生白`（CJK 字符
  之间的 `\CJKglue` 同样受影响，不限于中西文边界）；
- 不受影响：`虚室 \color{red}hello 生白`（`\color` 之后紧跟命令名而不是花括号，切分位置
  不变）、`\CJKunderdot{虚室 {hello} 生白}`（符号型命令不经 `ulem` 扫描）；
- oracle（同一正文不加任何装饰命令）：73。

真正的根因：`ulem` 按源码空格把正文切成一系列固定宽度的片段盒，落在片段盒内部的间距，
其收缩量被盒子的固定宽度吃掉，外层用不到。花括号使紧接其前的源码空格不再成为切分点，
于是该处 `\CJKecglue` 连自然宽度带收缩量一起进了盒内。判据是片段盒宽度
（`\showbox` + `showboxdepth=1`）：plain 为 `10 / 10 / 20.56 / 10 / 10`（pt），braced 为
`10 / 10 / 23.89 / 10 / 10`——片段盒**个数不变**，第三个正好多出 3.33pt，即那处间距的
自然宽度。另一条佐证：`虚室 {hello}`（有空格）与 `虚室{hello}`（无空格）切分完全相同，
说明那个空格已经不起作用。`\color` 形态不受影响的原因也在这里——空格之后紧跟命令名而
不是花括号，切分照旧（实测它多出一个 `x0.0` 的空片段盒，随后仍是 `x20.56`）。

## 核心教训：「代码路径被执行」不等于「它决定了结果」

这是本次反思最值得记录的一条，因为我自己第一次就把根因判断错了，是变异测试推翻的。

过程：我用探针三次确认编组情形会走到 `\@@_ulem_glue:n` 的 group tag 守卫的 MISMATCH
分支——`\l_@@_group_tag_tl` 记录的是 `T1L4`，当前分组是 `T1L5`（花括号让
`\tex_currentgrouplevel:D` 加深）。据此我认定「守卫拒绝搬运」就是根因，并按这个理解写
了用户手册说明。

推翻它的实验：把守卫绕过（改成无条件 `\UL@stop … \UL@start`），braced 的 `\badness`
**仍是 1000000**，读数一个字都没变。第一次只改了 `\@@_ulem_glue:n` 一处，我以为是漏改；
补上同一守卫的第二份 `\@@_boundary_use_ulem_glue:n` 后重做，结果依旧不变。两份都绕过而
现象不消失，才说明守卫与本问题无关。

教训应当写成：**「代码路径被执行」不等于「它决定了结果」**。插桩只能证明某个分支可达，
要证明它是成因，必须做变异测试——改掉它，看现象是否消失。这次连做三次插桩都指向同一个
错误结论，正是因为把「可达」当成了「归因」。这与 `lessons-learned.md` 里「现象、联系、
穷尽性、成因是四个独立命题」（#1046／#1047）同源，但更进一步：那条讲的是「A 缺了会坏」
不能推出「按某条件在 A、B 间分派」；这次是「A 会被走到」不能推出「A 决定了结果」——「可达
性」和「归因」是两件更容易被混为一谈的事，因为插桩本身看起来就像是在验证归因。

顺带说明：那个 group tag 守卫本身是必要的，只是它防的不是这件事——绕过它会让
`fntef-font01` 失败（字体从 `FandolKai` 退回 `FandolSong`），原因是 `ulem.sty:130-135`
里 `\UL@stop` 末尾的 `\egroup\egroup` 会退出两层分组，用户花括号插在中间时被连带退出。

另一条值得记的：`fntef-shrink01.lvt` TEST 9 的注释里原本也写着同一个错误归因（「group
tag 守卫据此拒绝搬运……这是刻意设计」），这次一并更正了。这说明**已有文档里的归因也
可能是错的，不能因为它写在测试注释里就直接采信**——测试注释和架构文档一样会漂移，
「稳定文档必须随实现演进重新核对」这条既有规则同样适用于测试文件内部的注释。

## 已排除的修法方向

1. 无条件走 `ulem` 通道——`fntef-font01` 失败（字体丢失）；
2. 记账后由下一个 `\UL@stop` 兑现——兑现位置与实际断行点无关，位置错了比不修更糟；
3. 搬运后恢复字体——不可穷尽（分组内可能改字体、颜色、字号，或任何局部状态）；
4. 在分组前输出 glue——时序上不可能：`ulem` 把 `{hello}` 当一个词整体处理
   （`ulem.sty:120` 的 `\@empty` 就是为了 preserve braces），花括号在片段盒内部才展开
   成分组。

还有一条基本事实：盒内 glue 的收缩量对外层**完全不可用**（手工对照 `A\hbox{\hskip 10pt
minus 5pt}B` 压窄 3pt 的 badness 是 1000000，而 `A\hskip 10pt minus 5pt B` 是 22），
所以没有折中方案。

要真正修好，需要让间距落到片段盒之外——改变切分时机，或改由 xeCJK 自己管理片段盒，那是
较大的结构改动。本次选择把限制、触发条件、判据与替代写法写进用户手册，并补回归测试守住
两侧，不改实现。

## Promotion Candidates

- **「代码路径被执行」不等于「它决定了结果」，归因必须靠变异测试确认。** 插桩证明分支
  可达，不证明该分支决定了观察到的现象；要证明因果，必须改掉那段代码看现象是否消失。
  这条与既有的「现象、联系、穷尽性、成因是四个独立命题」同属一组，但强调的失效模式不同：
  那条防的是从「A、B 都必要」跳到「按条件在 A、B 间分派」，这条防的是从「插桩证明分支
  可达」跳到「这个分支就是成因」——后者更容易被误认成已经完成了归因验证，因为插桩本身
  给出了看起来确凿的证据（分支确实被走到了）。
