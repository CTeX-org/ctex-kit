# #366 反思：zhnumber 新增算筹数字 `\zhrod`/`\zhrodbox`

## 任务

在 zhnumber 里实现算筹（中国古代记数符号）：可展开的 `\zhrod`（只产字符，供
`.toc`/PDF 书签等辅助文件使用）、不可展开的 `\zhrodbox`（切字体、压字距，负责
排版效果）、以及配置入口 `\zhrodsetup`（七个键：`units`/`zero`/`zerochar`/
`minus`/`font`/`kern`/`dot`）。键注册在独立模块 `zhnum / rod`，不混进既有的
`zhnum / options`。版本 3.2 → 3.3。落地提交 `086da209`（分支
`fix/366-zhnumber-counting-rod`）。

测试拆两处：`testfiles/rod-engine01.lvt` 与 `rod-engine02.lvt`（四引擎含 upTeX，只测引擎判定与报错）、
`testfiles-cjk/rod01.lvt` + `test/config-cjk.lua`（仅 xetex，测实际输出）。
两套 `l3build check` 全绿。

## Expected vs Actual

预期：按 issue 调研阶段留下的原型（`.llmdoc-tmp/investigations/366/`）与
issue 评论直接实现，键名照抄原帖建议（`[hv]`/`[vh]`）。

实际：调研阶段的两个关键结论都被最终实测推翻——原帖建议的选项字母顺序含义相反、
Unicode 区名与字形朝向相反；且原帖设想的"省零靠交替消歧"在穷举后被证明会产生
大量歧义，默认行为改为反直觉的"补零"。测试设计上也没有直接照搬 #1008 的现成
经验，而是重新独立踩中同一类坑（`\token_if_expandable_p:N` 对 protected 宏
恒真、`\tl_set:Ne` 捕获不触发报错），说明这两条规则尽管已写进 lessons-learned，
执行时仍需要主动回查才能避免重蹈。

## What Went Wrong

### 一、两处「名实相反」，且是同一功能里连续两次

1. **Unicode 区名与字形朝向相反**：`COUNTING ROD UNIT DIGIT`（U+1D360 起）实测
   是**横**画（`ht=4.05pt`，扁），`TENS DIGIT`（U+1D369 起）实测是**纵**画
   （`ht=8.03pt`，高）。换 `NotoSansSymbols2` 复核一致，确认是 Unicode 的编排
   而非某款字体的取舍。按区名直译（"个位用纵式所以取 UNIT 区"）会直接取反：
   我在 7 月的 issue 调研评论里就是这么写的，图里标的 `\zhrod[hv]{...}` 之所以
   看起来对，是因为原型代码本身也取反了两个区名而互相抵消，直到实现阶段按变量
   名重新核对字形才发现。
2. **原帖建议的接口名 `[hv]`/`[vh]` 字母顺序与含义相反**：原评论写
   `\zhrod[hv]{...} % 默认：个位纵、十位横`——但 `h` 在前却对应"个位纵"，
   字母顺序与其含义颠倒。调研阶段的原型照抄了这个命名。实现时改为
   `units=vertical|horizontal`，直接描述个位取哪一式，不再用需要记住对应关系
   的缩写。

同一个功能里接连两次名实相反（区名与字形反、选项字母与含义反），这不是巧合而
是提示：涉及"哪个名字对应哪个视觉方向"这类判断时，命名者的直觉和实测结果经常
不一致，必须每一处都单独核实，不能因为已经查过一处就假设另一处也顺理成章。

### 二、既有布尔量的语义边界比名字暗示的更窄

`\c_@@_unicode_engine_bool` 名字读起来像"是不是 Unicode 引擎"，实际判的是"是否
不必把汉字首字节设为活动字符"，因此把 upTeX（8-bit 但走双字节转义方案）也算作
真。而 upTeX 恰好**不能**表示 U+1D360 区——实测 `\char_generate:nn` 报
`Charcode requested out of engine range`。若直接复用这个布尔量，upTeX 会被
判定为"支持算筹"而走进正常路径，实际执行时才报引擎级错误。改为新增只含
xetex/luatex 的 `\c_@@_rod_engine_bool`。

这与 lessons-learned 已有的"复用带守卫的函数时，重新验证守卫在新调用点的前置
条件"是同一类问题在**判据**（而非函数）上的对应：那条讲守卫的强度随调用点
变化，这里讲的是布尔量的名字暗示的分类边界比代码实际实现的边界更宽——名字本身
就会误导判断，不需要"换调用点"这个动作，只读函数名就可能踩坑。

### 三、两处「断言看起来正规、实际零判别力」

1. `\token_if_expandable_p:N` 对 `\protected\long macro` 也答 yes——protected
   在它眼里仍算"可展开记号"这一类。拿它判"这个引擎下 `\zhrod` 是不是报错版本"
   时，支持与不支持的两个引擎读数相同，该项成了恒真断言。须改用
   `\token_if_protected_long_macro_p:N`（实测 protected 版下答 yes、可展开版
   答 no，两者才分开）。
2. **报错路径必须真的执行命令**。不支持的引擎下 `\zhrod` 是 protected 的，用
   `\tl_set:Ne` 捕获只会把 `\zhrod {12}` 原样存进变量而**不触发报错**——初版
   pdftex 基线里存的就是这个字符串本身，而不是报错信息，对"报错路径有没有接
   对"零判别力。

这两处都是先写出断言、生成基线后**读基线内容**才发现的，不是靠读代码发现的。
这与 #1008 反思里"观察不可展开命令的行为，只有'让它执行'一条路"是完全相同的
机制，且第 2 条几乎是同一情形的重演（`\tl_set:Ne`/`\tl_set:Nx` 捕获 protected
命令恒真）。#1008 反思已经把这条写进 lessons-learned 并特别记了"这条规律会在
同一批改动里复发"——本次不是在同一批改动里复发，而是在**另一个 issue**里
独立重新踩中同一个坑，说明仅仅把教训写进文档不足以让下一次实现自动避开它，
写断言时仍需要主动想到"这个命令是不是 protected，捕获手段拿到的是名字还是
结果"这个检查动作。

### 四、「一个例子成立」不等于「机制普遍成立」

Unicode 核心规范 22.2 用 6708 与 678 说明"靠纵横交替可以不写零也能区分"。据此
调研阶段一度考虑过默认省零（原型评论里用的正是缩小的〇，暗示零是可选/次要的）。
实现阶段穷举实测否证：**完全省零时 1..99999 内有 990 组碰撞**，`1`/`100`/
`10000` 的写法完全相同（都是单独一个纵式的一）。原因是交替只能区分**相邻**
位，不能定位数量级；规范那个例子成立是因为两数位数不同且零恰好在中间。故默认
`zero=fill` 写〇，省零降为 `zero=omit` 并在手册标明歧义。

这与 #1008 反思记的"引用统计数字前先确认量的就是所声称的那件事"同源但角度
不同：那条讲口径要对应所声称的性质，这条讲**从个例外推到普遍规律**——规范
文档给出的示例本身没有错，但示例成立的条件（位数不同、零在中间）没有被检验
是否是"任意输入下都成立"的一般条件，穷举后才发现它是个特例。

### 五、可展开性与排版效果互斥，分两层是本次的具体解法

实测对照（同一位置、两遍编译）：

| 形式 | 写进 `.toc` | PDF 书签 | `Token not allowed` 警告 |
|---|---|---|---|
| 纯可展开（只产字符） | 字面筹码 | 正确代理对 | **0** |
| 切字体 + 加字距 | `\rodbox {6}\rodbox {7}` | 退化 | **2** |

所以 `\zhrod` 只产字符、`\zhrodbox` 管排版。判据是"`.toc` 里是字符还是命令名"
加"`Token not allowed` 警告数"，两者都可复现。这个分层选择本身不是新教训——
#1008 已经在同一个包里因为"带选项的命令不可展开"踩过一次同类问题——但本次是
**在设计阶段主动应用**这条已知教训，而不是等实现完再补救，值得记下作为
"教训确实被下一个任务复用"的一个正例，与前面第三条"教训写了但没被应用"形成
对照。

实现细节上，`\zhrod` 对参数做了 `e` 展开（`\@@_rod_number:e`），照抄
`\zhdigits` 用 `\zhnum_digits:Ne` 的写法，没有重新踩 #1008 记的"用 `:n` 会把
`\zhrod{\arabic{section}}` 的字母参数当数字解析"这个坑——这也是一次教训被
成功复用的例子。

### 六、引擎判定选择"报错"而非"静默退化"

pdfTeX/upTeX 下 `\zhrod`/`\zhrodbox` 定义成直接报错的 protected 版本，而不是
退化成普通汉字数字。理由是算筹没有 8-bit 的替代记法，静默退化会让用户以为
自己排出了算筹，而实际排出的是完全不同的东西（普通数字）。这个决策没有被
逐轮推翻，一次到位，与前面几条反复否证的情况形成对比——区别在于"退化是否会
制造一个看起来对但实际错的输出"这件事本身可以从需求直接推出，不需要靠实测
才能发现，靠的是设计阶段的直接推理而非事后验证。

## Root Cause

本次绝大多数返工的共同根因是：**调研阶段（issue 评论）产出的原型代码和结论，
在实现阶段被当成了已验证的事实，而不是需要重新核实的候选**。原型的代码本身
含有两个互相抵消的错误（区名取反 + 接口字母取反），跑起来"看着对"，直到实现
阶段按变量语义重新核对才发现。调研调查报告和实现之间存在时间差（issue 评论
是 7 月的调研,落地是 8 月），这个时间差本身没有被当作"应该重新核对一遍关键
事实"的信号。

## Missing Docs or Signals

- 没有直接缺口——`\token_if_expandable_p:N` 对 protected 恒真、`\tl_set:Ne`
  捕获恒真这两条都已经写进 #1008 的反思和 lessons-learned，但落地时没有主动
  去检索"这个包里之前有没有类似的测试设计教训"就直接写了同款错误断言。这提示
  一个流程性缺口：**同一个包内新增功能时，若存在同包近期的反思文档，应当先读
  一遍再设计测试**，而不是仅凭对 expl3 的一般知识去写断言。这条已经在
  lessons-learned 里有"写下一条教训不等于已经把它应用到手头的产物上"的近似
  表述，但那条讲的是同一份改动内的复发，这次是跨 issue 的复发，值得留意这条
  规则的适用范围应该更宽。
- issue 调研评论本身没有任何机制提示"这份原型的结论有效期"或"落地前需要重新
  核对"。这类调研性 comment 目前是自然语言自由格式，没有区分"已验证的事实"
  与"待验证的假设"，两处名实相反的错误都藏在被当成事实陈述的句子里
  （"默认：个位纵、十位横"）。

## Promotion Candidates

以下几条建议提升到 `lessons-learned.md`；理由和不建议提升的部分分别说明。

**建议提升**：

1. **同一功能里出现一次"名字/朝向/方向类判断与实际相反"后，要对同一功能里其余
   同类判断逐一重新核实，不能假设只有一处**。本次区名反、接口字母反连续发生
   在同一个 `\zhrod` 功能里；这类"方向/朝向/顺序"型事实特别容易在直觉与实测
   之间出现系统性反转（不是随机出错），值得单独作为一条可复用的检查提示，区别
   于一般的"先验证再断言"规则——它更具体地指向"方向类判断成对出现时结伴出错"
   这个模式。
2. **调研阶段（issue 评论、原型）产出的结论落地前要重新核实，尤其是"看起来能
   跑通"的原型**。原型代码含有两个互相抵消的方向错误，运行结果因此"看起来对"，
   这比原型直接报错更危险，因为它不会主动提示自己有问题。这条具有跨任务复用
   价值：本仓库已有多个 issue 存在"调研 → 间隔数周 → 落地"的模式（如 #553、
   #347 的原型），落地时应视原型代码为候选而非已验证事实。
3. **已有布尔量的名字可能比它实际实现的分类边界更窄或更宽，判断能否复用要看
   实现而非名字**。这是对既有规则"复用带守卫的函数时重新验证守卫在新调用点的
   前置条件"的一个变体，把对象从"函数在新调用点"扩展到"布尔量的名字在新场景
   下"，两者共享"不能只读名字/不能只读原调用点的经验"这个核心，建议在
   lessons-learned 里相邻记录而不是合并，因为触发条件不同（一个是换调用点，
   一个是换判据使用场景，本次甚至没有换调用点，是第一次使用该判据）。

**只留在本反思，不建议提升**：

- "`\token_if_expandable_p:N` 对 protected 宏恒真"和"`\tl_set:Ne` 捕获
  protected 命令不触发报错"两条本身已经在 #1008 反思和 lessons-learned 里
  记录过，属于**同一条规则的第二次独立触发**，不需要在 lessons-learned 里
  再开一条——只需要确认这两条既有规则仍然成立、仍然值得引用即可。这里选择
  不提升的原因是新增第二个 Source 引用而非新增规则本身，比另立新条更合适；
  但如果 recorder 判断值得给这两条已有规则补一个 Source（本任务 #366），
  可以照做。
- "省零会产生歧义，穷举实测 990 组碰撞"是这次的具体数值结论，特定于算筹这个
  功能，不具有跨包复用价值，不建议提升为通用规则；但作为"一个例子成立不等于
  机制普遍成立"这条已有规则（源自 #1008 的统计口径教训）的又一个实例，可以
  在该规则的 Why 里补一句引用，不需要单独成条。
- "引擎判定选择报错而非静默退化"是一个设计决策，不是过程教训，且这类
  "接口能力缺失时报错优于退化"的原则在本仓库已有类似先例（#1041 的
  "把崩溃改成静默返回，往往比崩溃更糟"），本次是同一原则的正面应用（一次
  设计对了，不是踩坑后改的），不需要单独记录规则，值得记录的是它没有被推翻
  这一点本身，已经在本反思正文里说明。
